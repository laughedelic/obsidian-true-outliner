# What a cloud session can reach on GitHub

Why agent sessions kept breaking two conventions — branch names and attribution-free PR
descriptions — and what a Claude cloud session can and cannot do to the remote, measured so the
enforcement lands where it can work. Measured on 2026-09-20 in two cloud sessions on this
repository; the second is the one that produced this note.

## The two failures, in numbers

The remote held 12 `claude/*` branches against 4 `feat/` and 6 `chore/` (plus one
`entire/checkpoints/v1`), with CLAUDE.md naming the `feat/`, `fix/`, `chore/` rule the whole
time. Every one of the 12 came from a cloud session. The harness creates `claude/<two words>-<6
chars>` before the session starts and puts this in the session's system prompt:

> Develop on branch `claude/<words>` … NEVER push to a different branch without explicit
> permission

CLAUDE.md's rule loses to that directive every time: the directive asks for explicit permission
and CLAUDE.md never granted it. The claude.ai/code branch-prefix setting is one fixed prefix, not
a type prefix, so it cannot express the convention either.

The PR footer is the same shape. PR #173 was opened from a cloud session with the GitHub MCP
tool `create_pull_request`, with a body that ended in prose; the stored body came back ending in
`_Generated by [Claude Code](https://claude.ai/code/session_…)_`, session URL included. The
`attribution.*` settings in `.claude/settings.json` govern the CLI's own commit and `gh pr
create` paths; the MCP path is undocumented and ignores them. Rewriting the body with
`update_pull_request` sticks: the footer is not re-appended.

## What the session proxy allows

Every request leaves the session through a policy proxy (`/root/.ccr/README.md` on the VM). It
scopes GitHub access to the repositories attached to the session and to particular operations.
Each row below is one request from this session.

| Request | Result |
| --- | --- |
| `git push -u origin chore/cloud-session-conventions` (a branch the harness did not create) | `[new branch]` — pushes are not scoped to the harness branch |
| `git push origin --delete claude/…` | cut off by the proxy (first session); in this session the auto-mode classifier refused it first, as "Git Destructive" |
| `POST /repos/{o}/{r}/branches/{b}/rename`, `DELETE /repos/{o}/{r}/git/refs/heads/{b}` | "Write access to this GitHub API path is not permitted through this proxy" (first session) |
| `GET /user`, `GET /repos/{o}/{r}/pulls` (REST, this repository) | 200 |
| `PATCH /repos/{o}/{r}/pulls/174` with a body that has no footer, via `gh api` | 200, and the stored body ends in `---` and `_Generated by [Claude Code](https://claude.ai/code)_` — appended on every REST write, a clean body included |
| the same body through the MCP `update_pull_request` | stored as given; no footer |
| `POST /graphql` (any query) | 403: "GitHub GraphQL is not available from Claude Code sessions; use the REST API" |
| `GET /repos/cli/cli/releases/latest`, `GET /repos/github/gh-stack` (REST, other repositories) | 403: "GitHub access to this repository is not enabled for this session" |
| `https://github.com/cli/cli` (a page) | 403 |
| `https://github.com/{o}/{r}/releases/download/<tag>/<asset>` (any public repository) | 302 to `release-assets.githubusercontent.com`, then 200 |
| `https://cli.github.com/…` (the GitHub CLI's apt repository) | CONNECT refused: "policy denial" |
| `apt-get install gh` from Ubuntu's own repository | installs `gh 2.45.0` |

The last three rows decide how `gh` reaches a session: Ubuntu's package or a pinned release
tarball, never the documented apt source. `GH_TOKEN` and `GITHUB_TOKEN` are set on arrival and
`gh` reads them, so nothing logs in. `gh auth status` nonetheless reports "The token in GH_TOKEN
is invalid" — it validates through a path the proxy refuses — while `gh api user` returns the
owner's login, which is why `scripts/agent-setup.sh` checks with the latter.

## `gh stack` from the cloud

`gh extension install github/gh-stack` fails in a session: it starts with
`GET /repos/github/gh-stack/releases/latest`, which the proxy scopes out. The binary itself is
reachable — the release asset is named `linux-amd64` under each tag, and the download path is
allowed — so installing it by hand into `~/.local/share/gh/extensions/gh-stack/` with a
`manifest.yml` gives a working `gh stack version 0.1.1`.

It does not help. gh-stack reads every PR through GraphQL (`internal/github/github.go`,
`api.NewGraphQLClient`), and its first request on a real stack fails:

```
$ gh stack checkout 124
✗ failed to fetch PR details: fetching PR #165: querying PR #165: non-200 OK status code:
403 Forbidden body: "{\"message\":\"GitHub GraphQL is not available from Claude Code sessions …
```

`gh pr list`, `gh pr view 173` and `gh repo view` fail the same way. Nothing in this repository
or in the environment dialog changes that. The cloud-environments documentation
(code.claude.com/docs/en/cloud-environments, "GitHub proxy") states it: all GitHub operations go
through a dedicated proxy "independent of the environment's access level", the proxy "serves only
a pinned set of GraphQL operations for pull-request workflows" and rejects the rest with a 403
"regardless of the credentials you supply, so a `GH_TOKEN` you set gets the same 403". The
network access level (None, Trusted, Full, Custom) governs the session's own egress, which GitHub
traffic never uses, so a Custom allowlist naming `api.github.com` is a no-op here. The same
section documents the repository scope that blocks `gh extension install`, and a push protection
under which "`git push` works only against the session's current working branch" — our rename
before the first push keeps that branch current, which is consistent with the push above going
through. The one documented configuration without this proxy is a self-hosted environment,
which we do not run. So the extension is not installed in the cloud at all — neither by the
environment's setup script nor by the session hook — and CLAUDE.md's stack instructions give a
cloud session the layer's own work only, with a REST `gh api` listing in place of `gh pr list`. So a cloud session runs the half of the workflow that is REST and git: commit,
push, open and edit a PR through the MCP tools or `gh api`, read CI. Stack surgery stays in the
primary checkout, where CLAUDE.md already put it for a different reason. The session hook now
says so at start, so a session does not find out one failed command at a time.

## Why hooks, and not a CI check or a rename after the fact

Three places could hold the branch convention; only one is early enough.

- **CI** sees the name after a PR exists, which is after the name is fixed. A `claude/*` head
  cannot then be repaired from the session that owns it (renames and deletes are refused above),
  so a red check would strand exactly the sessions it is meant to correct, and a human would do
  the rename anyway. A rename at ready-for-review is harmful in its own way: a session told to
  keep pushing until CI is green recreates the old name on its next push, and the PR stops
  seeing its fixes.
- **A git-level rename** (push the new name, delete the old) does not retarget a PR; GitHub's
  rename (the PR header, or the REST endpoint from a machine with `gh` and no proxy) does, and
  the PR and its checks follow.
- **Hooks** run before the first push, while `git branch -m` still fixes everything. Hooks in
  `.claude/settings.json` do run in cloud sessions: the `SessionStart` hook's output is the
  first line of every cloud session's context, and the harness's own `PreToolUse` classifier
  refused a command in this session, so the tool-call path is live too. `scripts/agent-conventions.mjs`
  handles both events plus the PR footer:

| Input | Decision |
| --- | --- |
| `SessionStart` on `claude/probe-local` | prints the grant: rename to `<type>/<slug>` before the first push |
| `SessionStart` on `chore/…` | silent |
| `git push -u origin claude/x`, `git push origin HEAD:claude/x`, `git push --force-with-lease origin claude/x` | deny |
| `git push`, `git push -u origin HEAD` from a `claude/*` checkout | deny |
| the same two from a `chore/*` checkout | allow |
| `npm test && git push origin chore/y`, `git -C … push origin feat/z` | allow |
| `git push origin --delete claude/x`, `git push origin :claude/x` | allow — deleting one is the convention |
| `mcp__github__create_pull_request` with `head: claude/x`; `mcp__github__push_files` with `branch: claude/x` | deny |
| `mcp__github__push_files` with `branch: fix/x` | allow |
| `git push origin :claude/old fix/x:claude/new` (a delete beside a push) | deny — only the `:` refspec is exempt |
| `git push --all origin`, `--mirror`, a `refs/heads/*` refspec, with a local `claude/*` branch | deny; allow once no such branch exists |
| `git commit -m "git push origin claude/x"`, `git commit -m 'fix && git push origin claude/x'` | allow — quotes hide operators and words from the command lexer |
| `GIT_TRACE=1 git push origin claude/x`, `cd /x && git push origin claude/x`, `echo "a; b" \| git push origin HEAD:claude/x` | deny |

The guard reads the command with a small shell lexer — quotes group words and hide operators,
`VAR=value` prefixes and `git -C <dir>` are stepped over — rather than a regex over the whole
line. It does not expand `$(…)` or backticks, so a push assembled inside one passes; that is a
session working against its own hook, not a session missing a grant. The `PreToolUse` deny
carries the same grant as its reason, so the session that hits it has the rename in front of it. Denying a push is not stranding: the refused command is a `git push`, the
fix is a `git branch -m`, and both are local.

The PR footer goes the other way round: it cannot be prevented, only rewritten, and only through
one path. The footer is appended outside the session on creation, and this session's proxy
appends it again on every REST write to the body — the `PATCH` row above sent a clean body and
read the footer back. The MCP `update_pull_request` stores the body it is given, on PR #174 as
on #173. So the `PostToolUse` hook on `create_pull_request` writes nothing: it reads the new PR's
body with `gh api` and, when the footer is there (or `gh` is absent), tells the session to resend
the body through `update_pull_request`. PR #174, this change's own, went through exactly that:
created with the MCP tool, footer read back, footer gone after the MCP rewrite, footer back after
a REST `PATCH` of the clean body, gone again after a second MCP rewrite.

## Copilot

Copilot reads `.github/hooks/`, not `.claude/settings.json`, and its coding agent's branches are
named `copilot/<slug>` by GitHub. Whether that agent can rename its own branch was not measured;
until it is, a `copilot/*` head is renamed at landing from the PR header, which retargets the
PR. Its PR bodies carry no `Generated by` footer to strip.

## Housekeeping this leaves

- `claude/rename-probe` and the `claude/*` branches of merged PRs are deleted from the primary
  checkout; a session cannot. The beta sweep removes their prereleases once the branches are
  gone (`.github/workflows/beta.yml`).
- The harness branch of the session that wrote this note, `claude/sweet-mendel-e3qh6s`, is one
  of them: it holds no commits of its own, and the work went to
  `chore/cloud-session-conventions` by the rename this note describes.
- The auto-mode classifier's "Git Destructive" refusal sits above the proxy: a
  `permissions.allow` rule in `.claude/settings.json` (documented as honoured in cloud sessions)
  can pre-approve `git push origin --delete claude/*`, but the proxy's refusal beneath it is not
  ours to lift, so such a rule buys nothing until that changes.
